# Somnium — 글로벌 세계 시간 계약 v1.0 (설계 확정, 코드 미변경)

상태: 2026-10-23. **규범 문서**. 실제 마이그레이션/게임 동작은 아직 이 문서에 맞게 업데이트되지 않았다.

## 0. 결론과 단위

- **세계 시간 1단위 = 게임 내 1초**. `clock.elapsedUnits`의 앞으로의 의미는 **게임 내 경과 초**. 정식 구현에서는 `elapsedSeconds`로 이름과 타입을 명시하는 것을 권장한다.
- 1분=60초, 1시간=3,600초, 하루=86,400초. 정수 시간이며 소수 초는 저장하지 않는다.
- `turn`은 **커밋된 행동 처리의 누적 논리 턴**이고 초와 같은 단위가 아니다. 하나의 행동이 1턴/3초 또는 5턴/900초일 수 있다.
- 게임이 닫혀 있거나 UI를 보고 있을 때 현실 시간의 경과는 세계 시간에 영향을 주지 않는다. `Date.now()`를 사용해 월드 진행시키지 않는다.
- 사용자/OS 시간대, DST 또는 Windows 시계는 게임 시계에 영향이 없다.
- **UI는 '58단위'를 출력해서는 안 된다.** 세계 시각과 이동시간은 시/분/초, 긴 기간은 일/시간/분으로 표시한다.

## 1. 게임 날짜·시각

- 정본: `elapsedSeconds: nonnegative safe integer`과 `calendarId: 'somnium-calendar-v1'`.
- 새 게임의 표시상 시작 시간: **1일차 오전 08:00**. 구현에서는 `startSecondOfDay=28_800` 고정 상수를 사용해 `elapsedSeconds=0`을 표시 시각에 대응시킨다. 시작 시각을 사용자 선택형으로 확장할 때는 새 명시 필드/버전을 도입.
- `dayIndex = floor((28_800 + elapsedSeconds)/86_400)`, 1일부터 표시.
- `secondOfDay = (28_800 + elapsedSeconds)%86_400`.
- `hour=floor(secondOfDay/3600)`, `minute=floor(secondOfDay%3600/60)`.
- 현재 UI에서 별도 관리하는 `s.day`, `s.hour`는 정본이 아니며 위 값에서 **파생**해야 한다.
- 계절 길이, 월의 일수, 연도/윤년 등은 **본 계약에서 미확정**. 이들을 임의로 지구 달력처럼 가정하지 않는다.

## 2. 행동·시간 적용 계약

- 각 gameplay action은 `duration = {turns: positive safe integer, elapsedSeconds: nonnegative safe integer}`.
- 유효하지 않은 명령/잘못된 actor/디스패처 오류 → 상태/턴/시간/RNG 변화 없음.
- 사용자에게 비용이 있는 게임 내 실패 → 정책에 따라 턴/시간 정상 지불. 무효 입력과 구분.
- UI 탭 전환·아이템 상세 열람·경로 미리보기·일시정지·승인 전 확인 → **0턴/0초**.
- 승인된 정상 행동은 기존 `V2ActionDispatcher`가 한번만 턴과 초를 부과. UI나 핸들러는 시간을 또 더할 수 없음.
- 기존 `standardDuration = {turns:1,worldUnits:1}`은 **임시 폴백**일 뿐; 게임 내 행동 종류별 초 단위 정책을 정의한다. 값 1을 무조건 1초로 간주하는 이행은 금지.
- 유효한 게임 행동 중 '세계 시간 0초'를 허용하는 기술적 가능성은 보존하되, 생산/이동/전투 기본 정책에는 최소 1초를 강제할 것.
- 속도·숙련 보정은 턴과 경과 시간에 **독립된 정책**으로 적용; 계산은 정수로 반올림 규칙을 명시(권장: 최종 초는 올림).
- 긴 수면·이동·제작의 자동 처리에서는 초당 루프를 돌리지 않는다. 이벤트 큐/이벤트 발생 지점까지 점프. 플레이 중단 조건은 확정된 사건/행동 경계에서만 발동한다.
- 턴 기준 상태 이상(remainingTurns), 행동 기준 자동저장 카운터와 경과 시간 기준 효과를 혼합하지 않는다. 각각 용도를 표기하고 별도 회귀 테스트를 둔다.

## 3. 행동시간 데이터 (밸런스 제안, 확정값 아님)

| 행동 유형 | 임시 seconds | 비고 |
|---|---:|---|
| 전투 공격 | 3 | 1턴, 보정/장비/전투단계 별도 |
| 로컬 이동 1칸 | 6 | 1턴, 위험/지형 보정 가능 |
| 아이템 줍기/사용 | 5 | 아이템 종류별 정의 가능 |
| 약초 채집 | 120 | 장기 행동·중단 구조 연동 |
| 나무 벌목 | 600 | 실패/숙련 효과 분리 |
| 간단한 요리 | 900 | 제작의 실제 공정 데이터에서 결정 |
| 수면 | 21,600~28,800 | UI 스킵, 중간 사건 처리 |
이 숫자는 레퍼런스에서 복사한 규칙이 아니라 Somnium의 추후 밸런스용 시작 제안이다. 이번 설계 확정 범위는 **단위와 계산/저장 의미**, 개별 seconds 숫자는 아니다.

## 4. 03-B 장거리 이동 교통망

- 광역 지도 4×4 좌표/표시 위치는 거리를 결정하지 않는다. 세계관 지리/교통수단을 고려하여 **route별 travelSeconds** 명시.
- 기존 `RouteDefinition.worldUnits`는 과거의 추상 비용. **58 worldUnits를 58초/분으로 즉석 변환하지 않는다**.
- 시험용 여행 시간 (수정 제안): 거점~초원 900초(15분), 거점~숲 1500초(25분), 거점~강 2100초(35분), 숲~산맥 3900초(65분), 산맥~설원 12,600초(3시간 30분), 산맥~화산 28,800초(8시간), 강~해안 8100초(2시간 15분), 해안~바다 14,400초(4시간; 이동수단 필요), 해안~사막 28,800초(8시간). **예시용**이며 직접 연결 간선의 비용; 출발 거점~산맥 등의 전체 거리는 내부 경로 합으로 계산.
- `travelTicks/turns`는 내부 게임 진행/인카운터 평가 경계의 논리적 처리 단위이며, 세계 시계의 seconds와 무관하다.
- 이동 시작 전에 경로 preview는 합산된 초를 `약 N시간 M분`으로 표현. 사건이 없으면 여행을 빠르게 건너뛰어 한 커밋에서 전체 초를 적용하되, 이동 중 **교통 구간 완료마다** RNG 인카운터 판정. 실제 조우 발생까지의 초만 커밋.
- 이벤트가 발생하면 시간·턴·RNG·구간 위치·남은 여행을 **동일 트랜잭션의 상태**로 유지한다. 동일 시드+상태+경로 → 동일 판정. 재개 시 같은 구간을 다시 굴리지 않는다.
- 구간의 초 배분이 필요한 상황에는 `floor(totalSeconds * completedTurns / totalTurns) - floor(totalSeconds * previousTurns / totalTurns)` 사용. 모든 구간의 합은 정확히 travelSeconds. 정수 0초 중간 진행은 이동 콘텐츠 정책과 별도 검토.
- 인카운터 확률 12%/구간은 기존 03-B **시험값**이며 이 시간 계약에서 바꾸지 않는다. 이동 시간과 인카운터 확률을 섞어 해석하지 않는다(오랜 구간이 더 위험해야 하는지는 밸런스 단계의 별도 결정).
- 사용자가 이동 중인 장소의 임시 수명 종료를 판정할 때도 월드 경과 초 기준으로 판단.

## 5. 03-A 필드 수명·자원 갱신

- `createdAt`, `expiresAt`, `renewAt`, `lifetimeUnits`, `renewalUnits`, `regenerationUnits`는 새 버전에서 **세계 시계의 초**로 명시적으로 재정의/이름 변경한다.
- 기존 fixture의 `120/360/900` 단위는 **임시 실험 값**. 각각 2분/6분/15분으로 자동 해석하거나 초로 둔 채 사용하지 않는다.
- 제안 초기값: 약초 재생 1~3일(86,400~259,200초), 나무/광맥 재생 5~10일, 반복 던전 퇴장 후 3일, 임시 동굴 7~14일. **밸런스 제안**이지 본 계약의 확정 숫자가 아님.
- 상태 갱신은 `nowSeconds >= expiresAtSeconds` 등 **정수 누적 절대 시각** 비교로 결정. 플레이어 점유/퀘스트 보호 시 만료 대기. 방문·저장·재실행으로 시각이 초기화되지 않는다.
- 수면으로 8시간 이동 시 초 단위 28,800회 시뮬레이션하지 않고 만료·재생 경계 이벤트만 처리. 같은 시점 다중 이벤트의 결정적 순서(우선 순위+siteId)를 규정한다.
- 대규모 스킵 시 여러 주기가 경과할 경우 기존 `advanceSiteLifecycle`의 window 계산을 정수 초로 보존.

## 6. 저장 스키마와 이전 규칙 (필수)

현행 `SaveEnvelopeV2.saveVersion=2`, `GameStateV2.clock.elapsedUnits`는 **추상 단위**이므로 새로운 '초' 의미로 재해석하면 조용한 데이터 오염이다.

규범:
1. 기존 v1/v2 저장 파일·IndexedDB 스냅샷·revision은 변경/삭제하지 않는다.
2. **시간 의미를 식별 가능한 신규 스키마**를 사용한다. 권장 저장 envelope `saveVersion:3`, `schemaVersion:3`, `clock:{elapsedSeconds:number,calendarId:'somnium-calendar-v1',startSecondOfDay:28800}`. 실제 구현 전에 새 정식 state/decoder와 제한 규칙을 확정.
3. 새 GameState v3의 시간 의미는 전체 월드 스냅샷(여행 남은 비용, 필드 만료시각, 성장 일정 등)에 함께 적용. 시계만 바꾸고 다른 필드를 그대로 남기지 않는다.
4. **기존 v2의 elapsedUnits→seconds 단순 곱셈/대입 금지**. 기존 값의 실제 시간 의미는 정의되지 않았다. 자동 변환 실패가 아니라 *미결정 상태*로 취급.
5. 기존 세이브를 불러올 때는: (a) v2 레거시 모드로 원래 의미 보존하여 실행, 또는 (b) 사용자에게 시간계가 재기준화됨을 알리고 새 v3 복제 저장 생성. 어떤 의미의 변환인지 UI에 밝힌다. 원본 slot은 항상 보존; 마이그레이션은 새 slot/revision을 만든 뒤 승인할 때만 현재 상태 교체.
6. v2의 지역·아이템·RNG·턴 데이터는 호환 검증에 성공할 때만 복제하고 시계/필드수명/여행은 **각 필드별 이전 전략**을 따르게 한다. 이미 여행 중이거나 만료 시각이 있는 저장은 자동 승격 금지; 명시적 시나리오별 처리 없이 정식 완료로 간주하지 않음.
7. 구형 `s.day,s.hour`도 별도 목업 시계였으므로 전체 월드 시간의 정본으로 삼지 않는다.
8. 디코더는 미래 버전/알 수 없는 시간 필드/범위 초과를 거부한다. `Number.isSafeInteger`와 overflow 체크.
9. 생성기 버전·월드 상태 버전과 시계 버전을 구분. **시간 스키마 업그레이드 ≠ 맵 생성기 버전 변경**.
10. 구형 JSON 백업의 정보는 수정하지 않고 읽기 전 검증만 가능하게 보존. UI가 '복구 완료'라고 선언하기 전에 시간 이전 여부와 세계 상태 검증을 모두 완료해야 한다.

## 7. 구현 순서 및 승인 게이트

**T-1** 순수 시간 도메인: 상수, seconds 포맷, 날짜 파생, 범위 검사, 정수 duration, clock 버전.
**T-2** duration policy: 행동 유형별 초 정책(테스트 포함); 1턴/1초 폴백 제거. 실패·무효·UI 0시간.
**T-3** 이동 교통망: route.travelSeconds와 인카운터 중단, 여행 저장/재개와 RNG 재현.
**T-4** 필드 수명: 시간 단위/절대 시각/대규모 점프 갱신.
**T-5** v3 저장 계약과 v2→v3 명시적 비파괴 이전 UI. 손상 스냅샷 복구 승인 보호.
**T-6** 메인 UI 전면 시계 파생; Windows Chrome/Edge 연속 여행·수면·일일 경계·저장·불러오기 확인.

테스트 필수: `elapsed=0` 표시 첫날 08:00; 57,600초 후 다음날 00:00; 86,400초 후 2일차 08:00; 59→60초 분 전환; 23:59:59→00:00:00; 비용 합치기·인카운터 조기 중단; 시드 재현; 저장 취소·실패 시 원본 불변; 구형 v2 시간 단위 자동 재해석 거부; 큰 시간 스킵에서 필드 만료 이벤트 순서 검증.

## 8. 근거

CDDA는 턴제 생존 게임으로 기본 1초짜리 턴과 행동별 move cost를 분리하는 구조를 채택하지만, Somnium은 **1턴=1초**를 복제하지 않는다. 참고: https://github.com/CleverRaven/Cataclysm-DDA/wiki/FAQ-from-Discord 및 https://docs.cataclysmdda.org/design-balance-lore/design-user-experience.html .
