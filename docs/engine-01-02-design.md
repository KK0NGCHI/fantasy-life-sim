# 판타지 생활 시뮬레이션 — 게임 엔진 기술 설계서 01~02

기준 문서 v1.1 · 2026년 10월 22일 · 붙여넣은 검토안의 확정 결정·실제 구현 상태 반영

이번 설계는 기존 UI를 실제 게임 엔진에 연결하기 위한 기반입니다. 목표는 단순히 행동 버튼이 작동하게 만드는 것이 아니라, 나중에 농업·제작·탐험·전투·성장 시스템을 추가해도 핵심 구조를 다시 만들지 않도록 하는 것입니다.

먼저 기존 인수인계 자료의 핵심 규칙과 현재 GitHub 저장소를 대조했습니다. 과거에 전달받았던 ZIP 원본은 이번 세션에서 다시 열 수 없었으므로, 아래 문서는 확인 가능한 기존 결정 사항과 기술 레퍼런스를 바탕으로 작성한 검토안입니다. 원본의 세부 데이터 계약을 모두 재검증한 최종 확정본이라고 주장하지는 않겠습니다.

> **문서 우선순위**: 현재 구현 계약과 사용자의 확정 결정이 초기 검토 예시보다 우선합니다. 01-A 현행 계약: [src/engine/core/contracts.ts](../src/engine/core/contracts.ts), [docs/engine-01a.md](./engine-01a.md). 문서 안의 스키마·데이터 예시는 앞으로의 설계 제안이며 저장이나 게임 행동의 실제 구현을 의미하지 않습니다.

따라서 첫 번째 기술 원칙은 화면에 표시한 목업 수치가 실제 게임 규칙으로 굳어지지 않도록 분리하는 것입니다.

RogueBasin의 예시는 속도나 지연이 다른 턴 기반 게임을 다룹니다. 그러나 우리 게임에는 속도 스테이터스가 없으므로 그 스케줄러를 그대로 도입하는 것은 오히려 과도한 설계입니다. 행동 요청·실행·완료·취소를 명확하게 구분한다는 원리만 참고하는 편이 적절합니다.&#x20;


Redux에서 참고할 부분도 라이브러리 자체보다 순수한 상태 전환 원칙입니다. 기존 상태와 명령을 입력받아 다음 상태를 계산하도록 구성하면 저장, 테스트, 디버깅이 쉬워집니다.&#x20;


## 01. 공통 게임 엔진

### 3. 엔진의 중심 구조

다음 구조를 우선 추천합니다.

UI 입력

마우스 · 키보드 · 자동 진행

Action Dispatcher

명령 접수 및 순차 실행

Rules Engine

조건 검증 · 행동 결과 · 턴 처리 · 세계 변화

Game State

캐릭터 · 위치 · 인벤토리 · 세계 · 시계 · RNG

UI 갱신

화면 · 로그 · 상태

Save Manager

스냅샷 · 슬롯 · 백업

이 구조에서는 UI가 직접 HP를 변경하거나 턴을 증가시키지 않습니다. 예를 들어 농업 버튼을 클릭하더라도 UI가 하는 일은 `farm.tend` 명령을 보내는 것뿐입니다.

행동 결과를 결정하는 것은 엔진이고, UI는 엔진이 확정한 상태를 표시합니다.

### 4. 행동 처리 계약

기술적으로 가장 중요한 부분입니다.

```
type GameAction = {
  type: string;
  actorId: string;
  payload: Record<string, unknown>;
};

type DispatchResult =
  | { accepted: true; outcome: 'success' | 'failed'; turnsSpent: 1; nextState: GameState; events: GameEvent[] }
  | { accepted: false; reason: 'INVALID_COMMAND' | 'BUSY'; turnsSpent: 0 };
```

`GameAction`은 플레이어가 무엇을 시도했는지, `DispatchResult`는 엔진이 그것을 어떻게 처리했는지 나타냅니다.

세계 시간 변화량은 이후 세계 시계 규칙을 확정할 때 추가합니다. 현행 01-A 타입에는 아직 시간 변화량 필드가 없습니다.

예를 들어 던전에서 벽으로 이동하려고 하면 이동을 거부할 수 있습니다. 이러한 **게임 내 행동 시도 실패는 1턴을 소비**합니다. 다만 잘못된 데이터·존재하지 않는 명령·이미 처리 중인 요청처럼 기술적으로 접수 불가능한 명령은 행동으로 인정하지 않아 턴을 소비하지 않습니다.

반대로 제작이나 낚시가 성공하면 해당 행동 결과에 아이템 획득, 세계 시간 증가, 숙련 경험치 지급 같은 이벤트를 포함할 수 있습니다. 지급량과 성장 공식은 이 단계에서 결정하지 않습니다.

### 5. 턴과 세계 시간은 분리

저는 다음 3개를 서로 다른 값으로 두는 방안을 추천합니다.

| 필드            | 의미                | 예시           |
| ------------- | ----------------- | ------------ |
| `turn`        | 실제로 소비된 행동의 누적 횟수 | 153턴         |
| `worldTime`   | 게임 세계의 현재 시각      | 봄 12일 오전     |
| `elapsedTime` | 특정 행동으로 흐른 세계 시간  | 채집 행동의 시간 비용 |

접수된 게임 내 행동은 성공·실패에 관계없이 1턴을 소비합니다. 기술적 접수 거부는 턴을 소비하지 않습니다. 공통 처리기가 턴 수를 증가시키고, 행동별 시간 규칙이 정해져 있다면 세계 시계도 진행시킵니다.

여기서 한 가지 추가 제안이 있습니다. 내부 시간은 달력 문자열이 아니라 정수 단위의 누적 시간으로 저장하고, 계절·날짜·시각은 표시할 때 변환하는 것입니다. 시간 계산과 비교를 단순화할 수 있습니다.

다만 실제 달력의 연간 일수, 계절 길이, 행동별 경과 시간은 미정으로 남겨두겠습니다.

### 6. 자동 진행은 플레이어 행동을 반복 실행

자동 탐색을 별도의 게임 규칙으로 구현하는 것은 권하지 않습니다.

자동 탐색 컨트롤러가 매번 다음 행동을 선택하고, 일반 플레이어와 동일한 `Action Dispatcher`를 호출하게 만드는 편이 좋겠습니다. 그래야 수동 이동과 자동 이동의 턴·위험·상태 변화가 일치합니다.

자동 진행은 다음 조건을 검사해야 합니다.

1. 실행 전에 중단 조건을 확인합니다.
2. 실행할 다음 행동을 결정합니다.
3. 공통 행동 처리기에 명령을 보냅니다.
4. 행동 결과를 반영합니다.
5. 새로운 위험·상태 이상·자원 변화를 검사합니다.
6. 중단 조건이 없다면 다음 반복으로 넘어갑니다.

중단 조건 검사 시점은 행동 이전과 이후 모두 필요합니다. 예를 들어 이동 후 적을 발견했는데 그 결과를 반영하기 전에 다음 자동 이동이 실행되어서는 안 됩니다.

자동 진행은 긴 동기 반복문으로 실행하기보다, 화면이 반응할 수 있도록 행동 단위로 진행해야 합니다. 중단·저장·사용자 입력을 처리할 수 있어야 하기 때문입니다.

### 7. 이벤트와 게임 로그 분리

엔진 이벤트와 사용자에게 보여주는 로그는 다른 개념으로 다루는 것이 좋겠습니다.

가령 플레이어가 광석을 채집했다면 엔진 내부에서는 다음과 같은 사실이 발생합니다.

```
{
  "type": "item.acquired",
  "itemDefId": "core:iron_ore",
  "quantity": 2
}
```

로그 시스템은 이를 바탕으로 `철광석 2개 획득`이라는 메시지를 만들어 표시합니다.

이렇게 분리하면 로그의 문구를 바꿔도 게임 규칙이 변경되지 않고, 반복 메시지를 묶어도 실제 아이템 지급 기록이 사라지지 않습니다.

다만 이벤트 전체를 영구 보존해야 하는 것은 아닙니다. 저장 가능한 현재 상태를 기준으로 하고, 최근 로그와 중요한 사건 기록을 별도로 관리하는 방식을 추천합니다. 모든 행동을 처음부터 다시 실행해 상태를 복원하는 Event Sourcing은 현 단계에서 필요하지 않습니다.

이것은 Redux가 권장하는 상태 구조와도 일치하는 방향입니다. 상태는 화면 컴포넌트가 아니라 데이터 도메인에 따라 구성해야 합니다.&#x20;


## 02. 저장 시스템과 데이터 구조

### 8. 저장 방식 비교

웹 기반 싱글플레이 게임이라는 조건에서 3가지 저장 방식을 비교했습니다.

| 방식             | 장점                       | 단점                           | 판단        |
| -------------- | ------------------------ | ---------------------------- | --------- |
| `localStorage` | 간단하고 현재 목업에 이미 사용 중      | 용량이 작고 동기식이며 대규모 게임 데이터에 부적합 | UI 설정용    |
| IndexedDB      | 구조화 데이터, 비동기 처리, 트랜잭션 지원 | 구현과 버전 관리가 다소 복잡             | 게임 저장용 추천 |
| 외부 JSON 파일     | 백업, 복원, 사용자 직접 보관 가능     | 자동 저장용으로는 불편                 | 백업·이동용 추천 |

MDN은 `localStorage`와 `sessionStorage`의 용량이 상대적으로 작으며, 더 큰 구조화 데이터에는 IndexedDB를 사용하는 편이 적합하다고 안내합니다. IndexedDB는 트랜잭션을 지원하므로 세이브 데이터를 여러 부분으로 나누어 기록할 때 일관성을 유지하는 데도 유리합니다.&#x20;


따라서 초기 설계에서는 IndexedDB + 외부 세이브 파일을 추천합니다. 서버나 계정 시스템은 현재 게임 목표에 필수적이지 않습니다.

### 9. 세이브 슬롯 구조

현재 기획에는 퀵세이브, 수동 저장, 자동 저장이 모두 필요합니다. 다만 슬롯 수를 임의로 확정하지는 않겠습니다.

우선 각 세이브는 다음과 같은 메타데이터를 갖도록 설계할 수 있습니다.

```
{
  "format": "fantasy-life-save",
  "saveVersion": 1,
  "slotId": "manual-001",
  "saveType": "manual",
  "savedAt": "2026-10-22T12:00:00Z",
  "gameTurn": 153,
  "contentVersion": "prototype",
  "gameState": {}
}
```

위 값은 구조 설명용 예시입니다.

핵심은 `saveVersion`과 `contentVersion`을 분리한다는 점입니다.

- `saveVersion`: 세이브 파일 자체의 구조 버전
- `contentVersion`: 저장 당시 사용한 게임 콘텐츠 데이터 버전

예를 들어 새로운 장비 슬롯이 추가되면 세이브 구조를 변경해야 할 수 있습니다. 반면 기존 장비의 공격력만 조정했다면 세이브 구조는 그대로일 수 있습니다.

이 둘을 같은 버전으로 묶지 않는 편이 향후 업데이트에 유리합니다.

### 10. 저장 데이터는 화면이 아니라 게임 상태를 중심으로

전체 게임 상태는 다음과 같은 영역으로 나누는 것을 추천합니다.

```
interface GameState {
  meta: GameMeta;
  clock: WorldClock;
  rng: RandomState;
  player: PlayerState;
  inventory: InventoryState;
  world: WorldState;
  progression: ProgressionState;
  flags: GameFlags;
}
```

이름과 세부 필드는 검토안이며 실제 타입은 기획 문서의 데이터 계약과 맞춰 확정해야 합니다.

각 영역의 역할은 다음과 같습니다.

| 영역            | 저장할 정보                |
| ------------- | --------------------- |
| `meta`        | 게임 식별자, 세이브 구조 버전 등   |
| `clock`       | 누적 턴, 세계 시계, 계절 관련 상태 |
| `rng`         | 난수 생성기 상태             |
| `player`      | 캐릭터 정보, HP, MP, 상태 이상 |
| `inventory`   | 소유 아이템과 수량, 개별 인스턴스   |
| `world`       | 지역 방문, 던전, 지형 및 세계 변화 |
| `progression` | 숙련·경험치·해금·발견 진행도      |
| `flags`       | 퀘스트·이벤트 등에 필요한 상태     |

반면 색상 팔레트, 창 크기, 로그 패널 높이 등은 게임 진행 데이터와 분리하는 것이 좋겠습니다. 이러한 설정은 특정 캐릭터의 성장 기록이 아니라 사용자의 인터페이스 환경이기 때문입니다.

### 11. 아이템 종류와 개별 인스턴스

여기는 기존 기획과 직접 연결되는 부분입니다.

하나의 아이템 종류를 정의한 데이터와, 플레이어가 실제로 소유한 개별 아이템을 구분해야 합니다.

아이템 정의 — 정적 콘텐츠

ID: `core:iron_sword`

이름: 철제 검

분류: 무기

기본 태그: `weapon:sword`

개별 아이템 A

ID: `item-001`

소재: 철

품질: 예시 값

인챈트: 없음

개별 아이템 B

ID: `item-002`

소재: 다른 소재

품질: 예시 값

인챈트: 있음

이 구조라면 아이템 정의를 수정하면서도 개별 아이템이 갖고 있는 소재나 인챈트 정보를 유지할 수 있습니다.

또한 서로 완전히 동일한 소모품은 수량으로 관리하고, 품질·내구도·인챈트 등이 서로 다른 아이템은 개별 인스턴스로 관리하도록 확장할 수 있습니다.

단, 어떤 아이템을 중첩할 수 있는지 판단하는 규칙은 아이템 시스템 설계 단계에서 결정해야 합니다. 지금은 그 판단에 필요한 데이터 구조만 마련하면 됩니다.

### 12. 저장 파일 버전과 마이그레이션

저장 구조가 변경되었을 때 기존 세이브를 어떻게 처리할지도 02단계에서 설계해야 합니다.

다음 순서를 권장합니다.

세이브 읽기

파일 형식과 버전 검사

필요하면 이전 버전 → 최신 버전 변환

데이터 유효성 검사

문제가 없을 때만 게임 상태 교체

세이브 파일을 읽었다고 즉시 현재 게임 상태를 덮어쓰지 않아야 합니다. 변환 또는 검증에 실패하면 원래 상태를 유지하고, 어떤 문제가 있었는지 알려야 합니다.

Ajv는 JSON Schema를 사용해 데이터의 타입, 필수 속성, 수량 범위 등을 검증할 수 있습니다. 따라서 세이브 파일과 게임 콘텐츠의 기본 구조를 확인하는 데 사용할 후보입니다.&#x20;


특히 저장 파일은 다음 3종의 버전 문제를 구분해야 합니다.

| 상황                  | 처리 원칙                  |
| ------------------- | ---------------------- |
| 구버전 세이브             | 지원하는 마이그레이션 경로가 있다면 변환 |
| 손상된 세이브             | 현재 데이터를 변경하지 않고 오류 표시  |
| 현재 게임보다 새로운 버전의 세이브 | 무리하게 불러오지 않고 호환성 오류 표시 |

기본적으로 이전 파일을 변환하기 전에 원본을 보존하는 편이 좋습니다.

### 13. 저장 중단과 데이터 손상 방지

브라우저 저장소를 사용하면 단순히 `save()` 함수를 호출했다는 이유로 저장 완료를 표시해서는 안 됩니다.

IndexedDB 트랜잭션의 `complete` 이벤트를 확인한 뒤 저장 성공을 알리는 구조가 필요합니다. MDN 역시 트랜잭션 완료와 개별 요청의 성공을 구분합니다.&#x20;


또한 브라우저를 종료하는 순간에만 저장하는 설계는 위험합니다. 페이지 종료 과정에서는 비동기 저장 작업의 완료를 보장할 수 없기 때문입니다.&#x20;


추천하는 보호 장치는 다음과 같습니다.

- 저장 슬롯마다 최신 정상 스냅샷을 보존할 수 있는 구조
- 저장 실패 시 이전 정상 세이브 유지
- 저장 중복 실행 방지
- 파일 내보내기 및 가져오기
- 저장 오류 시 명확한 사용자 알림
- 동일 세이브를 여러 브라우저 탭에서 동시에 수정하는 상황의 충돌 방지

여기서 자동 저장 간격과 백업 보존 개수는 아직 결정하지 않겠습니다.

마지막으로 IndexedDB도 브라우저 정책, 저장 공간 부족, 사용자 삭제에 영향을 받을 수 있습니다. 따라서 외부 파일 백업을 지원하는 것이 중요합니다. MDN은 일반 브라우저 저장소가 기본적으로 저장 공간 회수 대상이 될 수 있으며, 필요한 경우 지속 저장 권한을 요청하는 방법을 설명합니다.&#x20;


## 14. 기술 스택 비교 및 선택안

기존 UI는 별도 빌드 과정이 없는 JavaScript ES Modules 기반입니다. 여기서 게임 엔진을 구현할 때 어떤 기술을 추가할지 결정해야 합니다.

| 분야     | 후보                           | 제안                  |
| ------ | ---------------------------- | ------------------- |
| 언어     | JavaScript / TypeScript      | TypeScript 추천       |
| 상태 관리  | 직접 구현 / Redux Toolkit        | 초기에는 경량 자체 엔진       |
| 게임 규칙  | UI 내부 처리 / 독립 모듈             | 독립 모듈               |
| 저장소    | localStorage / IndexedDB     | IndexedDB           |
| 데이터 검증 | 직접 검사 / JSON Schema + Ajv    | JSON Schema + Ajv   |
| 테스트    | Node 테스트 / Vitest            | 초기에는 Node 기본 테스트 러너 |
| 난수     | `Math.random()` / 시드 기반 PRNG | 시드 기반 PRNG          |

TypeScript를 추천하는 이유는 앞으로 아이템·캐릭터·세계 상태의 필드가 많아질 것이기 때문입니다. 데이터 구조가 변경되었을 때 연결된 코드에서 오류를 찾기 쉽습니다.

다만 기존 UI를 전면 재작성하자는 의미는 아닙니다. 새 엔진을 TypeScript로 작성하고 기존 JavaScript UI와 연결하는 점진적 전환이 적합합니다.

Redux Toolkit도 충분히 좋은 선택이지만, 현재 게임은 서버 동기화나 여러 독립 화면의 복잡한 상태 갱신보다 하나의 게임 상태를 순차적으로 변화시키는 것이 중심입니다. 그래서 처음부터 Redux를 도입하지 않고, Redux의 설계 원칙을 적용한 자체 게임 상태 처리기를 만드는 안을 우선 추천합니다.

시드 기반 난수 생성기는 특히 중요합니다. 같은 초기 상태·명령·난수 상태에서 같은 결과가 나오는 구조를 만들면 버그 재현과 자동 테스트가 쉬워집니다. 관련 테스트에는 `fast-check` 같은 속성 기반 테스트 도구를 추가할 수 있습니다.&#x20;


## 15. 개발 단위와 완료 기준

01\~02단계를 다음과 같이 나누어 구현하는 것이 좋겠습니다.

| 단계   | 구현 범위            | 완료 기준                     |
| ---- | ---------------- | ------------------------- |
| 01-A | TypeScript 개발 환경, 게임 상태·명령 타입 계약 | 엄격 타입 검사·빌드·기본 테스트 성공 (행동 실행은 01-B)       |
| 01-B | 행동 실행·실패 턴 소비·이벤트 | 성공/실패 턴 처리 및 상태 원자성 |
| 01-C | 세계 시계·난수·자동 진행 제어      | 두 난수 스트림 재현, 설정형 장기 행동 턴·자동 중단 검증    |
| 02-A | 콘텐츠 정의 및 인스턴스    | 종류 ID와 개별 아이템 구별          |
| 02-B | 세이브 저장·로드        | 저장 후 새로고침해도 상태 복원         |
| 02-C | 슬롯·파일 입출력·마이그레이션 | 여러 저장 유형, 외부 백업, 버전 검증    |
| 02-D | 통합 테스트           | 오류·중복 실행·손상 데이터 처리 검증     |

가장 먼저 만들 통합 테스트는 실제 콘텐츠가 아니라 작은 시험용 행동 3개면 충분합니다.

예를 들어 이동, 자원 획득, 휴식을 공통 엔진으로 실행해 봅니다. 그다음 저장 후 다시 불러와 플레이어 위치·턴·세계 시계·소지품·난수 상태가 일치하는지 검사합니다.

완료 기준에는 다음과 같은 성질을 포함하는 것이 좋겠습니다.

- 잘못된 행동은 게임 상태를 부분적으로 변경하지 않는다.
- 하나의 행동이 중복 실행되어 턴이 2번 증가하지 않는다.
- 자동 진행은 수동 진행과 동일한 규칙을 사용한다.
- 저장과 불러오기 전후의 핵심 게임 상태가 일치한다.
- 손상된 저장 파일이 기존 정상 세이브를 덮어쓰지 않는다.
- 성장 공식이나 경제 수치가 없는 상태에서도 공통 엔진을 테스트할 수 있다.

이 기준을 충족하면 이후 농업·제작·탐험 시스템을 독립적으로 추가할 수 있는 기초가 마련됩니다.

## 16. 설계 결정 정리

여기까지 조사한 결과를 바탕으로, 저는 다음 사항을 01\~02단계의 기술적 채택 후보로 정리하겠습니다.

| 결정 항목  | 추천안                       | 근거                      |
| ------ | ------------------------- | ----------------------- |
| 엔진 구조  | UI와 분리된 단일 게임 상태 및 행동 처리기 | Redux 상태 관리 원칙          |
| 행동 처리  | 검증 → 실행 → 턴·시간·이벤트 적용     | 기존 턴 기획 + 턴 스케줄링 사례     |
| 자동화    | 일반 행동 처리기를 반복 호출          | 수동·자동 행동 일관성            |
| 저장     | IndexedDB + 외부 파일         | MDN 저장소·트랜잭션 문서         |
| 데이터    | 정적 정의 + 개별 인스턴스           | 기존 아이템 기획               |
| 저장 안정성 | 스냅샷·버전 검사·검증 후 로드         | IndexedDB + JSON Schema |
| 언어     | 엔진만 TypeScript로 점진적 전환    | 복잡한 상태 계약 관리            |
| 테스트    | 순수 로직 테스트 + 저장 통합 테스트     | Redux·fast-check 설계 원칙  |

여기서 제가 확정하지 않은 게임 규칙은 행동별 세계 시간 비용, 달력 세부 규칙, 자동 저장 간격, 아이템 중첩 조건, 성장 및 경제 공식입니다.

이 중 일부는 엔진의 구조만 먼저 구현하면 나중에 결정할 수 있습니다.

## 확정 결정 및 현재 진행 상태

- 실패 행동: **게임 내 행동으로 접수된 시도가 실패해도 1턴 소비**, 기술적 접수 거절은 0턴. 01-B 구현·테스트 완료.
- 저장: **IndexedDB + 외부 JSON 백업 파일**. 02단계에서 구현.
- 언어: TypeScript 엔진, 기존 JavaScript UI 유지.
- **01-A와 01-B 완료**, 01-C는 기획 합의 단계이며 구현 전.
- **01-C 합의 사항은 [engine-01c-design.md](./engine-01c-design.md)를 우선 적용**: 기본 1턴, 일부 긴 작업은 숙련에 따라 짧아지는 다중 턴 범위, 종류별 세계 시간, 행동할 때만 시계 진행, 세계/행동 RNG 분리, DCSS형 위험 지형 자동 회피, HP·MP·허기 비율 중단, 정보창 열람 시 자동 진행 일시 정지·명시적 재개.
- 아직 미정: 긴 작업 턴 범위/감소 공식, 세계 시간 단위 및 달력 길이, 숙련 성장 공식, 경제, 아이템 중첩·품질 계수, 저장 슬롯·자동 저장 주기.

## 01-C 확정 결정 및 작업 분기 (2026-10-22)

- 기본 행동 1턴. 낚시·채광 등 장기 행동은 숙련이 상승할수록 **최소·최대 턴이 함께 감소하는 설정형 범위**에서 난수로 턴 소비량 결정. 구체적인 기간·숙련 성장 공식은 미정.
- 월드 생성과 행동 RNG 두 개의 독립 스트림. 버전 지정 xorshift32 시제품 구현, 재현 및 저장 가능 상태 계약을 02단계에서 검증.
- 세계 시간은 턴과 독립적인 누적 단위. 행동할 때만 진행하고, UI 조회나 방치로는 진행하지 않음. 행동별 세계 시간 비용은 정책으로 주입.
- 자동 경로 선택은 알려진 위험 지형을 회피(DCSS 참고). HP·MP·허기 중단 임계값은 설정에서 사용자 지정 비율로 입력.
- 정보창 열림과 백그라운드 전환 시 자동 행동은 **일시 정지**하며, 사용자가 명시적으로 재개해야 다시 실행됨.
